# 分析延迟优化实测（2026-09-22）

## 计时口径

界面的“排队+分析 N ms” = 分析结束时 SystemClock.elapsedRealtime() − 该 I420 帧克隆完毕后提交算法队列时的 elapsedRealtime()。

包含队列等待、两次检测的 JNI/图像预处理/NPU 运行/输出复制与解码、逐目标特征提取与匹配、跟踪状态计算。此前的传感器曝光/USB/Camera2 传输、YUV 到 I420 转换以及克隆操作不在其中；UI 主线程排队与实际屏幕刷新也不在其中。这不是纯 NPU 时间，也不是动作开始至商品卡展示的端到端时间。

DetectCamPerf 的 secondary_decode 包含主检测的 Java 解码和第二检测完整调用/解码；primary 包含主检测 JNI 全过程。其余列为 features（提取+匹配）、queue（算法队列等待）、other（其余分析）。因此不能把 primary 数值写成纯 NPU 推理时间。

## 改动

检查 CMake 编译命令确认 JNI 原生桥原先按 Debug 默认 -O0 编译。YUV 像素转换、缩放等循环在每个模型调用重复执行，成为主要开销。新增 target_compile_options(smartcam_rknn PRIVATE -O3)，重建并更新项目自带 arm64 原生库。没有启用 fast-math。

保留 FP16 双检测模型、1280×720 相机、640 检测输入、原有特征库及匹配门限；两个检测器仍逐分析帧运行，没有跳过检测来降低显示数字。界面将原来的笼统毫秒标签明确为“排队+分析”。

## 板端样本

RK3588 orangepi5ultra / Android 13 / 外置 USB Camera2。前后均为实拍，现场有人移动商品和杂物，并非固定输入的严格 A/B 实验。日志是从板端环形缓冲读回的一段连续样本；各剔除前 5 条，不能据此保证长期最大延迟。

原始计时文本及统计分别在 performance-before/after.log 和 .json。脚本 scripts/summarize_performance.py 可按 pid 复算，P95 采用 nearest-rank。
